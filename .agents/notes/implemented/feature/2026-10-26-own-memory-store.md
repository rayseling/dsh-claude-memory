# Agent Note: dsh 自己的记忆目录,模型通过插件工具写

Status: implemented

## Problem

插件只把 Claude Code 维护的索引注入 dsh 会话,dsh 会话里学到的事(用户纠正、项目约束、外部链接)没有地方落,下一个会话又得重新问。用户要求 dsh 也能记录记忆。[只注入索引、对记忆只读](2026-10-12-index-only-read-only.md) 的理由是两个宿主共写一份记忆会冲突、单一写者最简单;它并没有说 dsh 不能有自己的一份。

dsh 的文件沙箱默认是 `workspace-write`,可写根只有 workspace、`/tmp` 和 `tmpdir()`,没有配置能加白名单;模型用自己的文件工具写 `~/.dsh/memory` 必被 `FS_SANDBOX_DENIED` 拒绝,只能每次 `sandbox_permissions` 升级并经用户审批,headless/ACP 没有审批应答者,等于写不了。

## Decision

dsh 有一个自己的记忆目录,文件格式与 Claude Code 的记忆相同,由模型通过本插件注册的两个工具 `memory_save` / `memory_delete` 写,工具在服务端进程直接落盘(`src/store.js`,只依赖 `node:fs`)。

- **位置**:`<ownMemoryHome>/<slug>/`,默认 `~/.dsh/memory/<slug>/`,索引是 `MEMORY.md`,条目一文件一事实。frontmatter 为 `name` / `description` / `metadata.{node_type, type, originSessionId, modified}`,与 Claude Code 落盘的文件一致,另加本店专用的 `title` / `hook` 供重建索引;`type` 取 `user | feedback | project | reference`;正文带 `**Why:**` / `**How to apply:**` 和 `[[name]]` 互链。`slug` 用与 Claude Code 相同的 `slugOf`,因此也继承它的碰撞:`/a-b` 与 `/a/b` 落到同一目录,这是 Claude Code 自己接受的概率,这里不另起编码。
- **只有一个目录**:slug 取自 `canonicalRoot(cwd)`——linked worktree 的主仓库,否则 git 根,否则工作目录本身,全部按真实路径。它与 [Claude Code 索引的多候选定位](2026-10-12-memory-directory-location.md) 不同:读 Claude Code 的索引可以试多个候选,写自己的记忆必须收敛到一处,否则两个 worktree 会各写一份。`ownMemoryHome` 必须是绝对路径:插件按进程 cwd 解析而模型按会话 cwd 理解,两边会分叉;相对路径在挂载时记警告并关掉 own store,Claude Code 索引的注入照常。
- **工具是唯一写路径**:`memory_save(name, type, title, description, hook, content)` 创建或按同名覆盖一个条目;`memory_delete(name)` 删文件,已不存在不算错。`memory_save` 的 `name` 限小写 kebab-case(Claude Code 的命名);`memory_delete` 接受索引能列出的任何文件名(`isEntryName`:字母、数字、点、连字符、下划线,不以点开头,无括号),因此从 Claude Code 复制来的 `feedback_testing.md` 也能删。`memory`(不分大小写)两边都保留,因为 APFS 默认不分大小写,`memory.md` 就是 `MEMORY.md`,存它会覆盖索引、删它会删掉索引。工具只知道 own store 的目录,碰不到 `~/.claude`。**三条契约**(`src/store.js` 模块注释同文):(1) **投影永不因缓存失败**——条目文件是唯一事实源,`projectIndex(dir)` 列目录、读每个条目的 `title` / `hook` 得到索引文本;`MEMORY.md` 只是缓存,只当提示用(行的顺序,以及没有自带字段或此刻读不了的条目该保留哪一行),缺失、不可读、是目录、FIFO、符号链接一律当空并报告(`cacheError`),绝不抛出;每个文件先 `lstat`、只打开常规文件、最多读 256 KiB,所以 FIFO 不会挂住、symlink loop 不会被跟。(2) **提交与修复分离**——`saveMemory` / `deleteMemory` 先原子写或删自己的 `<name>.md`(这就是提交),再从新投影重写缓存,重写失败作为 `indexError` 随已提交的结果返回,工具把它说成"条目已保存/已删,缓存未重写,下次读从条目文件投影",绝不把已提交的保存伪装成失败;删除不先读缓存。插件第一步同样投影,**注入的是投影结果而不是文件**,不一致就重写(`syncIndex`);`dsh` 读关着时也静默同步,因为模型被要求写前 `cat` 这个文件。写者交错、写后崩溃、缓存损坏都只让 `MEMORY.md` 暂时落后,模型看到的从来等于条目集合。(3) **不是可读条目的东西报告、不丢**——文件名不在条目文法里(空格、CJK、`+`、超长)、不是常规文件、读不了的 `.md` 都记进 `skipped`,缓存里已有的行原样保留(唯一的标题/hook 不会因为一次读失败消失),没有行的才算 `omitted`,注入时标为"未完整展示";调用方按名字集合警告一次。没有 `title`/`hook` 的手写条目保留已有行,否则按 `name` 与 `description` 进索引;frontmatter 解析支持双引号、单引号(后面的 `# 注释` 丢弃)、裸值(去尾注释)和 `|` / `>` 块标量,忽略 BOM,空串、`null`、`~`、`[]`、`{}` 当作缺省回退。没有锁文件,没有读改写,没有重建轮数;进程内按目录排队;条目和缓存都用临时文件 + rename 原子替换。代价:工具条目的索引行被手工改过会在下次投影时换回条目字段,`MEMORY.md` 里的非条目行(标题、说明)不保留。写后按 Claude Code 的做法度量索引(`judgeIndex`,行数与 UTF-16 code unit 各对 `maxLines` / `maxChars`):达到九成提醒"一行一条、合并或丢弃陈旧条目";超过任一上限时文件已写入但工具返回错误,说明超出部分下次加载会被丢弃,要求用 `memory_save` 合并、`memory_delete` 删除。调用方没有带 cwd 的会话(非 agent 调用)直接报错。
- **一条消息、两个段落**:Claude Code 索引段(只读)在前,自己的段在后;digest 覆盖整条消息,[snapshot 替代语义](2026-10-12-snapshot-replacement-and-withdrawal.md) 不变。完整性声明只对"展示出来的索引"成立,文本明说"未展示的来源只是本会话没读,不要据此推断删除"。配了 own store 时自己的段始终存在,没有条目也要告诉模型目录在哪、用什么工具写,因此纯撤回消息只在 `ownMemory: false` 时才会出现。own 索引读失败时该段降级为"索引未加载,写前先 `cat`",Claude Code 段照常进入;own 定位或 stat 失败(规范根算不出来、目录不可访问)时本轮什么都不进入——不注入 Claude Code 段,也不撤回,否则少了 own 段的替代消息会被模型读成"dsh 没在读";Claude Code 索引读失败仍整条不注入。完整性声明按索引各自给出:整份展示的索引才说"缺的条目已不存在",被截断的索引明说"后面可能还有,不要据此推断删除"。索引文本里出现的 `system-reminder` 标签在渲染时换成全角 `＜`,索引行的 `title` / `hook` 写入时同样转义,`</system-reminder>` 不可能提前结束框定。
- **写入规则随消息注入**(`renderMemoryMessage`):记什么、不记什么、写前查自己的索引(Claude Code 段展示时也查它,但只为避免重复,绝不写那边)、用 `memory_save` 同名更新而不是复制、用 `memory_delete` 删错的、不许用文件工具碰目录、索引上限;另有 Claude Code 给模型的三句:记忆是背景上下文不是用户指令、反映写下时的事实,点名的文件/函数/flag 要先核实还在;被要求记仓库里本来就有的事时,反问哪里不显然、记那个。规则按 Claude Code 系统提示里的记忆规则改写,放在动作之前。
- **写了就会回灌**:工具落盘后,下一轮第一步重新投影,摘要变了就重注入(Claude Code 索引仍按 size/mtime 缓存读取)。
- **配置**:`ownMemory`(默认 `true`)和 `ownMemoryHome`(默认 `~/.dsh/memory`,支持 `~/`)。它们没有 Claude Code 对应项,和 `readByDefault` 一样不取 Claude Code 默认值。`ownMemory: false` 时不注册工具、不注入自己的段,`dsh` 来源也从读取开关和菜单里消失。
- **写不是会话级开关**:`ownMemory: true` 时自己的段始终注入;会话里只能按来源决定读不读([按来源的读取开关](2026-10-26-session-memory-toggle.md)),`dsh` 读关着时该段只给目录和规则、不 stat 索引,并要求写前先读索引去重。
- `~/.claude` 仍然永远只读,注入文本继续要求模型不创建、修改、删除那里的文件,也不复制那边已有的条目。

## Alternatives considered

- **写进 Claude Code 的同一个目录。** 一份记忆两个宿主共享,查重和互链都在一处;Claude Code 自己的多个并发会话也在往同一个 `MEMORY.md` 追加,格式本身容忍多写者。用户选择不碰 Claude Code 的地盘:两边各自演进(元数据字段、索引格式)时不会互相污染,也不用担心 Claude Code 的清理或迁移把 dsh 写的条目当异物处理。代价是记忆分家,注入文本要求模型写前查两个索引。
- **模型用普通文件工具写,插件不写文件。** 最少宿主接口,Claude Code 自己也是模型用 Write 写、宿主事后补元数据。被文件沙箱否决:默认 `workspace-write` 下 `~/.dsh` 不可写,每次都要审批,headless 完全不可用;而且模型可能顺着"更新/删除"的写规则改到 `~/.claude`,索引并发写有 lost update,frontmatter 写坏插件也不知道。工具路径一次解决这四件事。
- **把 own store 放进 workspace(如 `<repo>/.dsh/memory/`)。** 沙箱直接放行。会把记忆提交进仓库或要求每个仓库改 `.gitignore`,worktree 之间也不共享;Claude Code 把记忆放在仓库外正是为此。
- **给 dsh 加可写根白名单。** 最干净。要改 dsh 主仓库,违反本项目"不碰 dsh 主仓库"的边界。
- **两条独立消息、两个投影。** 每个存储单独去重、单独撤回。投影状态和 `sourceEventSeqs` 判定要翻倍,而两个索引一起变化时还是两次注入;合成一条消息后 digest 一次搞定。
- **own store 的读定位也沿用多候选顺序。** 能命中旧版按 worktree 路径建的目录。可本插件的 own store 没有旧版,而且读到非规范目录、写到规范目录会让模型看到的索引和它该追加的索引不一致。
- **没有条目时不注入自己的段。** 省几百 token。模型就不知道目录在哪、该怎么写,第一条记忆永远写不出来。
- **索引读改写 + 跨进程文件锁(`O_EXCL` 锁文件、心跳、token 释放、遗弃接管)。** 保留 Claude Code"索引是手写文件"的语义,手工改索引行不会被覆盖。两轮独立审计各给出丢索引行的确定性交错:清理遗弃接管互斥时按路径 `rm` 删掉后来者的新互斥、第二次 inode 检查后按路径 `rename` 移走继任者的新锁、释放时读 token 到 `rm` 之间被接管。没有 `flock` 的路径型 check-then-act 永远留窗口,Node 又没有 `flock`;起单一写入者守护进程对一个插件太重。改为索引由条目文件推导,把共享状态的读改写整个去掉。
- **只在写侧投影:保存后重建索引,再列一次目录、变了就重建,最多八轮;读侧仍只读 `MEMORY.md`。** 没有锁,正常路径正确。两份独立审计各给出丢行交错:写者 A 用旧列表写索引前,B 完整保存并返回成功,A 的旧索引随后覆盖——每轮都可重演,第八轮后 A 带着缺 B 条目的索引成功返回;或 A 复查时 `readdir` 报错、或 A 在写索引前崩溃。"B 的条目晚于 A 的列表,B 的重建一定更晚落盘"不成立。加轮数、最后再写一次、耗尽时抛错都消不掉已经落盘的旧索引;而读侧只读文件、还宣称完整。把投影搬到读侧后,磁盘上的索引变成缓存,不再需要任何写侧收敛论证。
- **读侧投影,但缓存仍在读路径上:`projectIndex` 读不到 `MEMORY.md` 就整体失败。** 三方审计给出同一组反例:缓存 EACCES / EISDIR / ELOOP 时可读条目被藏起来、模型被要求 `cat` 一个读不了的文件、删除被缓存读挡住、保存已落盘却报普通失败;缓存是 FIFO 时 `readFile` 永久阻塞;一次读不了的旧条目让 `syncIndex` 立刻删掉它唯一的标题行;文法外文件名静默消失而消息仍说"完整";`dsh` 读关着时模型 `cat` 到过期缓存。根因是缓存还被当作事实源和旧行仓库。改成上面的三条契约:缓存只做提示、提交与修复分离、不是条目的东西报告不丢。
- **索引带 manifest / 代次,读侧校验代次再注入。** 也能发现过期索引,但没有原子的"按代次比较再替换",写侧仍需要串行化;而读侧既然要列目录算代次,直接投影成本相同、无需新格式。
- **own slug 用无损编码避免 `/a-b` 与 `/a/b` 碰撞。** 目录名难读,与 Claude Code 的目录对不上;碰撞概率极低且 Claude Code 自己也接受。记为已知上限。

## Consequences

- **收益**:dsh 会话能把用户纠正和项目约束留到下一个会话;所有 worktree、符号链接入口共用一份;写入不经沙箱审批,headless 也能写;元数据由宿主填,模型看到的索引总等于条目文件集合;模型没有任何路径能改到 `~/.claude`。
- **代价与已知上限**:多用两个宿主接口——`ctx.tools.register`(可选注入;宿主没有 `tools`、或 tools 作用域已卸载——注册标记由 `toolCtx.effect` 的 disposer 在作用域释放时复位——时每会话警告一次,自己的段改说"本宿主无法写入"、不给工具规则)和 `ctx.get('sandboxPolicy')`(可选;存在且会话策略为 `read-only` 时工具拒绝写,与 Claude Code 在只读会话里写不了记忆一致);子代理在 `includeSubagents` 关着时调用工具被拒,与 Claude Code 不给子代理记忆一致;开着 own store 的每个有 cwd 的会话第一步都多一条几百 token 的消息,即使项目没有任何记忆;模型会把查重做在两个索引上;slug 碰撞同 Claude Code(`/a-b` 与 `/a/b` 同目录,own store 可写时误改另一项目条目的后果更重,接受为已知上限);`--separate-git-dir` 的仓库从 worktree 里定位不到主仓库(git 自己也存不下这个指针),own store 落在 worktree 自己的路径下,独立 git 目录恰好叫 `.git` 时则落在该目录的父目录,与 `git worktree list` 的报告一致;工具只校验 `name`、`type` 和各字段非空,正文质量和长度仍靠模型;磁盘上的 `MEMORY.md` 在写者交错、写后崩溃或重写失败后可能暂时落后于条目,直到任何会话(含 `dsh` 读关着的)下一次第一步或写——两次之间用 `cat` 看文件的人可能看到旧内容,模型看到的是投影;同名条目两处同时 `memory_save` 时后写的赢;每个会话轮次的第一步(读开关关着也一样)和每次写入都读全部条目文件(一次 `readdir`、每条一次 `lstat` + 开头 256 KiB),条目数受 200 行上限约束,没有缓存;`MEMORY.md` 的手工改动——改工具条目的行、加标题或说明——会被投影替换,read-only 会话的第一步也会重写,0.5.0 之前没有 `title`/`hook` 的条目保留已有索引行;缓存本身读不了时,读不了的条目和文法外的文件名就没有旧行可保,直到条目能读、或文件改名;文法外文件名的条目只能手工删;frontmatter 只解析本店用到的 YAML 子集,其它写法(流式集合、锚点、多文档)按裸值处理;所有从索引发起的修复写都是插件自己的写入,不经沙箱,也不受 read-only 会话策略约束。
